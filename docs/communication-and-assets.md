# 运营交互与任务资产规则

## 目标

面向普通运营和实习助理：少阅读、少输入、少重复确认。正文只提供当前阶段必须知道和必须处理的内容；完整证据、原始模型响应和调试信息写入任务资产目录。

## 对话原则

根据当前阶段使用短段落或紧凑表格，不强制每次使用相同标题。审批时直接展示需要看的方案、实际图片或关键异常，并在末尾提出明确的下一步问题。以下只作可选例子：

```markdown
## 当前状态：<阶段> · <状态>

<一句话结果或一张小表格>

<只在目录首次出现时给出任务资产绝对路径>

<是否按此方案与预估费用先生成代表图？>
```

规则：

- 任务资产目录首次出现或路径变化时给出一次绝对路径；不要每轮重复打印。
- 文件名和子目录使用中文；代码、模型名、API 字段和必要的原始文件名可以保留英文。
- 不输出内部思考、长篇提示词、完整 API 响应、重复的已确认事实或过程流水账。
- 审批问题要描述“批准什么”和“批准后会自动做什么”；代表图批准后同轮继续生成余图，不让用户再回复“继续”。
- 只有出现阻塞、预算、风险或需要用户决策时才打断用户。
- 视觉方案使用视觉方案板：编号、缩略图/占位、发布用途、展示任务、文案状态、场景和状态一屏可读。

## 任务资产目录

每次套图任务只使用一个用户可见根目录，固定命名为：

```text
<用户项目目录>/任务资产与审批/
```

首次使用自动创建。固定结构：

```text
任务资产与审批/
├── 01_原始素材/
│   └── <套图名称>/
├── 02_代表图审批/
│   └── <套图名称>/
├── 03_最终套图/
│   └── <套图名称>/
├── 04_记录与报告/
└── README.md
```

用户主要查看 `02_代表图审批/<套图名称>/` 和 `03_最终套图/<套图名称>/`。代表图审批目录保留未批准草稿；仅把批准的版本复制进最终套图。识别、方案、费用和质检记录放在 `04_记录与报告/`，按文件名区分。

原始素材规则：用户可以自行把素材放入 `01_原始素材/<套图名称>/`，也可以要求 Agent 整理。用户从项目目录外提供素材时，Agent 应复制到对应套图文件夹；用户已放入目录的文件尽量原地保留，不改名、不移动，除非用户明确要求整理。

代表图和最终套图由 Agent 自动整理到对应的 `<套图名称>/` 文件夹。最终套图文件夹同时放入套图图片、`套图总览.jpg` 和 `最终审核报告.md`，让用户只进入一个文件夹即可查看最终结果。

每个任务的文件名使用序号和中文用途，例如：`01_商品主视觉.png`、`02_细节图.png`、`套图总览.jpg`。记录与报告直接散放在 `04_记录与报告/`，用 `商品识别_<套图名称>.json`、`方案摘要_<套图名称>.md`、`整套初筛_<套图名称>.json` 等名字区分套图和批次；记录过多时再增加批次子目录。

## 多模态与结构化响应

多模态模型输出应优先要求固定 JSON 结构，再由 Agent 渲染成上面的短回复和视觉方案板。JSON 是内部接口，不直接展示给普通运营。字段至少区分 `facts`、`inferences`、`unknowns`、`risks`、`next_action` 和 `confidence`。

## 文案策略

每张图增加 `文案状态`：`用户已提供`、`系统建议待确认`、`明确无文案`、`不适合加文案`。

- 用户提供明确文案：原文、语言、大小写和禁改部分锁定；先检查是否符合发布用途，再规划层级、字体气质、字号、字距、留白、对比度和与产品的遮挡关系。
- 用户未提供文案：默认不擅自把功能、材质、尺寸、性能或节日促销词写进图。系统可根据已确认商品事实提出最多 1–3 条短文案候选，标记“建议文案”，在代表图生成前与套图方案一起确认。
- 用户明确说不要文案：所有相关图片无文字；首图等本来不适合文字的发布用途默认无文字。
- 文字由生图模型渲染时，生成后必须 OCR 检查；关键文案优先使用确定性排版/后期合成路径，避免把错字当成合格成品。
- 文案和装饰元素必须服务于一个展示任务；不使用无事实依据的徽章、排名、保证、认证、尺寸或性能数字。
