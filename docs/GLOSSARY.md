# Amazon Gallery Studio 术语与审批规则

本文件是规范性定义，用于统一 Agent、脚本、用户简报和 README 中的概念。与 `README.md` 的简明术语表冲突时，以本文件为准；与用户明确且合法的要求冲突时，以用户要求为准，但不得绕过平台规则与真实费用授权。

## 1. 角色与对象

### Agent
执行本 Skill 的 AI 客户端（OpenCode、Codex、Claude Code、Cursor 等）。Agent 负责识图、规划、生成、质检、归档与向用户简报；不拥有代替用户批准费用的权力。

**不能混淆**：Agent 自动完成的检查、方案或生成成功，都不是用户批准，也不是 Amazon 审核。

### Skill / Skill Home
Skill 是包含 `SKILL.md`、`scripts/`、`references/`、`requirements.txt` 的可安装目录。Skill Home 是它被安装到的位置（例如 `~/.agents/skills/amazon-gallery-studio/`）。
Skill Home **只存程序与静态资源**，不存商品图、生成图或任务记录。

### Workspace（任务工作区）
用户商品项目所在目录。所有任务资产放在 `<workspace>/任务资产与审批/`。Workspace 与 Skill Home 必须分离。显式指定的已有工作区必须包含 `.gallery-project-root` 标记。

### Gallery（套图）
一次完整的商品套图任务，有稳定 `task_id`、一个产品名、一份冻结方案和一套审批/请求记录。一个工作区可以有多套 Gallery，按产品名区分子目录。

### Image Task（逐图任务）
Gallery 内有固定 `display_number` 的一张图，至少包含：`id`（如 `img-03`）、用途、展示目的、场景、构图、比例、像素目标、参考图 ID、文案状态与约束。编号一旦批准不得重排。

**不能混淆**：图片文件版本（v01、v02）不是新的 Image Task；重做同一编号仍属于该任务。

### Representative（代表图）
从已冻结的逐图任务中选出的**一张**样张，用于先验证商品保真与视觉方向。代表图属于最终套图，保留其原始编号；它不是额外的第 N+1 张。

规则：

- Agent 依据可解释评分选择，不硬编码第 1 张。
- 用户批准后，该**具体版本**被复制到最终套图的正确编号；批量阶段不重复生成它。
- 用户不满意时生成新版本（v02…），旧版本保留，不覆盖。
- “批准代表图”只针对所展示的版本与绑定方案；方案或版本变化后旧批准失效。

### Product Profile（商品档案）
识图后保存的商品事实基线：产品名、可见事实、推断与置信度、未知项、SKU/颜色映射、参考图哈希与关联、识图模型与调用记录。
`visible_facts` 是图中可观察事实；`inferences` 是推测；`unknowns` 不得被后续文案当作事实。

### 产品原始参考图
用户提供的真实商品照片。系统只复制，不移动、不压缩、不覆盖源文件。派生转换文件必须记录，原图保留。

## 2. 图片用途

### Amazon MAIN（官方首图）
Listing 的第一张官方图片。按目标站点和类目执行白底、仅商品、无叠字等规则。规则可能变化，最终以卖家后台为准。

### Listing 副图
详情页其余图片，可展示场景、细节、配色、用途、包装等，不因“主图套系”这一口语而强制白底。

### 白底主图（White Background MAIN Image）
以纯白或近纯白背景展示商品、用于 Amazon 官方 MAIN 的首图。候选必须通过分辨率、边缘背景、完整性、道具/文字、构图与商品匹配检查；仅“四角是白色”不构成合格结论。

### 原图复用（Source Image Reuse）
直接将用户提供的白底候选复制为最终套图中的 MAIN，不调用生图 API、不占用付费生图次数。复用文件必须在最终目录保留来源文件名与 SHA-256；不得冒充 AI 新生成。
代表图选择会排除复用任务；多色商品不得用一个颜色的白底图代表其他颜色。

### 修整（Retouching）
对基本可用但存在比例、背景边缘、构图或裁切问题的白底候选做付费编辑。必须保留原图、生成新版本，且不得改变商品结构、颜色、材质或细节。修整占用付费调用与预算。

### 新生成（New Generation）
重新调用生图模型制作白底 MAIN。仅在无可用候选、用户明确要求，或候选无法修复时使用。

### 广告 / 站外图
用于广告或社媒的图片，可以有更强氛围与文案；仍不得改变真实商品或虚构卖点。

**不能混淆**：口语“主图”可能指整套图片，也可能指官方 MAIN。只有明确 `Amazon MAIN` 才触发严格白底约束；场景集合图应标为副图/广告图。已有白底图的复用/修整/新生成/不纳入是四个不同决策；复用不产生生图费用，修整与新生成产生费用。

## 3. 审批与授权

### 方案确认（Plan Approval）
用户接受当前版本的逐图任务、比例、文案处理和费用范围。程序保存：

- `plan_version` 与 `plan_hash`（只对设计内容计算，不含运行时进度字段）
- `authorized_image_calls`（本套最多生图调用次数）
- `cost_quote_status` = `verified | estimated | unavailable`
- 用户原话 `user_expression`

**不等于**：无限付费授权、对后续方案修改的预先批准、对生成结果的验收。

### 生图费用授权
首次或新增生图前，用户必须看到“将调用其 API Key 产生真实费用”的说明与调用上限。方案确认可包含代表图及已说明的批量范围；若原范围不足，必须补充授权。

**程序约束**：每次生图前写入 `pending` 请求并检查授权次数，超过即抛出 `BudgetError`；不依赖 Agent 自觉。

### 代表图批准（Representative Approval）
用户明确认可某个代表图版本。程序绑定 `representative_image_id`、文件名、SHA-256、方案版本与哈希。

代表图批准后，Agent 应在同一轮继续生成其余已授权编号，不要求用户再回复“继续”。

### 整套通过（Gallery Approval）
用户明确说“通过”“这套可以”等，表示接受当前整套结果（可包含已知问题）。若仍有缺失编号，需要用户明确接受部分交付（`--accept-partial`）。

明确说“开始下一套/下一个产品”时，视为上一套通过并归档，然后开启新任务；“看看下一套方案”之类的探索性表达不构成通过。

**不能混淆**：自动视觉初审通过、技术检查通过、生成成功，都不等于整套通过。

## 4. 视觉审核

### 原图识别（QA-1）
生成前，用多模态模型实际读取全部相关参考图，输出产品档案。未实际读取像素时不得声称完成识别；部分图片失败时标记 `partial_vision`。

### 自动初审（Visual QA）
对照原图检查成品，状态：

- `pass`：未发现明显问题，可交人工审批
- `revise`：发现需修改的问题
- `uncertain`：证据不足或模型不确定
- `unavailable`：无法读取/调用失败

报告应包含具体问题、位置、证据与置信度；没有明显问题不要编造。

### 技术检查
确定性检查：文件存在、实际像素、比例、格式、MAIN 白底角、文案 OCR 等。状态为 `technical_pass` / `technical_fail`。

### 人工终审
用户对整套的最终确认。自动审核只提供证据，不替代人工判断，也不构成 Amazon 合规结论。

**不能混淆**：`pass` 不是“用户已批准”，也不是“Amazon 已审核通过”。

## 5. 费用与次数

### generated_calls
实际发起的生图调用次数（含代表图与返工）。

### vision_calls
识图与审图调用次数。后台执行，不逐次弹费用提醒，但必须记录。

### rework_calls
定向返工的生图调用。与首次生成合并计入生图授权上限。

### 生成调用上限（authorized_image_calls）
本套允许的最大付费生图/修整调用次数；原图复用不计入。最终交付总数 = 复用数 + 修整数 + 新生成数。默认建议为“目标张数 + 5 次定向返工”，但**默认值不等于授权**；必须由用户确认后写入审批记录。允许用户授权少于目标张数，此时达到上限会停止并交付已完成部分。

### 总预算（authorized_total_cost_usd）
用户接受的总费用上限（可选）。`cost_quote_status=unavailable` 时不得填写虚假金额，应使用调用次数兜底。

### 费用状态
`known_usd` 为已知金额；未知费用记为 `unknown`，绝不能记 $0。请求状态包含 `pending / succeeded / failed / unknown`。`unknown` 表示可能已扣费但本地未确认，禁止自动重试。

## 6. 文件与恢复

### 四类一级目录
固定为 `01_原始素材`、`02_代表图审批`、`03_最终套图`、`04_记录与报告`，每类下按**同一产品名**建立子目录。不得改成“产品名/四类目录”，也不得增加普通用户可见的第五类。

### 版本
代表图使用 `NN_用途_v01.png`、`_v02.png`；不覆盖历史版本。最终图使用 `NN_用途.png`。

### 待审候选
整套通过前，批量生成的图片放在 `03_最终套图/<产品>/待审候选/`；通过后复制/移动到产品目录并写入 `最终审核报告.md`。不得把未通过图片标成“已通过”。

### 断点续跑
`task.json` 保存状态、方案版本与预算；`api-requests.json` 保存请求账本；已存在的成品按编号跳过，不重复扣费。请求结果未知时进入 `blocked`，不得自动重发。

### 部分交付
中断或达到预算时，仍生成当前可用的总览与报告，列出已完成、未完成编号和费用状态。

## 7. 状态机

正常路径：

```text
importing → recognizing → planning → plan_pending_approval → plan_approved
→ representative_generating → representative_reviewed → representative_pending_approval
→ representative_approved → batch_generating → gallery_qa
→ gallery_pending_approval → gallery_approved
```

异常状态：`blocked`、`partial`、`failed`、`resume_pending`、`cancelled`。每个状态都必须能从 `task.json` 恢复，不依赖对话记忆。

## 8. 典型歧义

- **“继续”**：只表示继续当前已授权流程，不扩张预算或新增图片类型。
- **“都试一版”**：若产生额外生图调用，必须说明新增次数与费用并取得授权。
- **“主图”**：先确认是官方 MAIN 还是整套图片的口语称呼；只有前者触发白底硬规则。
- **“看起来是实木”**：属于推断，不得写成材质事实或文案卖点。
- **“通过”**：只对该阶段有效；方案通过不代表代表图通过，代表图通过不代表整套通过。
- **“开始下一套”**：上一套视为用户通过并归档；仍需保留其全部缺陷记录。
- **“有白底图就用”**：表示接受复用推荐，但仍需方案中展示的检查结论；不代表允许跳过修整或费用授权。
- **“白底图不用做”**：记录为本次不纳入白底 MAIN，不再重复询问，也不擅自新增。
- **未知尺寸/材质**：没有实测数据时不得编造；测试用示意尺寸必须标注“示意、不可直接发布”。

## 9. 责任边界

| 事项 | Agent | 用户 |
| --- | --- | --- |
| 识图、规划、生成、质检、归档 | 负责 | 可提出修改 |
| 商品事实与卖点真实性 | 不编造、标注未知 | 最终确认 |
| 生图费用 | 事前说明、记录、执行上限 | 明确授权 |
| 方案与代表图 | 提供证据与建议 | 批准/修改 |
| Amazon 合规 | 提示风险、不冒充审核 | 上架前自行核查 |
| 源文件 | 只复制、不覆盖 | 保留原始素材 |
