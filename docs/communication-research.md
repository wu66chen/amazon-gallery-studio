# 跨 Agent 运营交互方案调研摘要

## 结论

最适合本项目的是“**固定短版回复协议 + 结构化内部数据 + 可选视觉方案板 + 中文任务资产目录**”的组合，而不是依赖某个 Agent 的隐藏思考或专属 UI。

## 参考原则

1. OpenAI Model Spec 将“尽可能有帮助但不过度越界”“表达不确定性”“工具选择正确”“高效而充分”列为默认行为；这支持把冗长过程放在内部记录，把不确定性保留在短摘要里。
2. OpenAI Prompt Engineering 文档建议把开发者规则与用户输入分离，使用清晰的 Markdown/XML 边界、少量高质量示例，并为生产提示词建立评估集；本项目应把回复格式作为开发者级规则，把商品和任务作为运行时输入。
3. OpenAI Structured Outputs 文档建议用 JSON Schema 约束模型输出，避免模型漏字段或生成非法状态；Tokease 兼容性未完全确认，因此实现上应先要求 JSON，再做本地 schema 校验和降级解析。
4. OpenAI Agentic prompting 建议长任务明确阶段、使用进度记录和关键节点提示；本项目把这些变成用户可见的“当前状态”和“需要你做”，不把完整过程倾倒给运营人员。

## 方案比较

| 方案 | 优点 | 局限 | 建议 |
|---|---|---|---|
| 自由 Markdown | 所有 Agent 都能显示，最容易实现 | 模型容易重复、遗漏审批问题、格式漂移 | 只作降级输出 |
| 固定短版 Markdown 协议 | 跨客户端、易读、无需专属 UI、可测试 | 需要 Skill 严格控制字段和长度 | **作为默认方案** |
| JSON Schema 内部状态 | 状态、文案、审批门和预算易被程序处理 | 不能直接给普通用户看；中转站未必支持严格 schema | **作为内部数据协议** |
| HTML/图片视觉方案板 | 方案更直观，普通运营更容易审批 | 部分 Agent 不渲染 HTML/附件；需提供 Markdown 降级 | **可选增强** |
| 隐藏思考/内部日志 | 减少用户噪音，保留调试证据 | 不应依赖客户端是否展示隐藏思考；可能产生隐私/成本问题 | 只保存结构化审计记录，不依赖隐藏思考 |

## 推荐协议

面向用户只输出：

1. 当前状态
2. 一句话结论
3. 最多三项待办
4. 一个任务资产目录绝对路径
5. 最多三个关键文件
6. 以“是否同意？”或“是否批准？”结束的明确问题

其余内容写入 `任务资产与审批/04_记录与报告/`，并用 JSON 保存：`facts`、`inferences`、`unknowns`、`risks`、`next_action`、`confidence`、`approval_state`、`copy_status`。

## 文案流程建议

- **用户有文案**：原文锁定；先做发布用途检查，再做字体、层级、字距、留白、对比度和装饰关系；生成后 OCR。
- **用户无文案**：默认不向首图和事实型图片添加文字；对适合文案的副图最多给三条基于已确认事实的短文案候选，标记待确认；代表图前必须确认。
- **用户明确不要文案**：进入“明确无文案”状态，后续不再重复询问。
- **文案无法可靠生成**：优先生成无文字画面，之后用确定性排版工具合成；不得把错字图当成合格成品。
